# Truth-Talk Azure Production Provisioning Runbook

**As of:** 2026-10-27  
**Audience:** Truth-Talk owner, Azure subscription administrator, application operator  
**Status:** Architecture and implementation runbook; no resources have been provisioned.  
**Scope:** Azure-hosted Truth-Talk web delivery and a gated, future Truth-Talk-owned application data plane. This runbook is not authorization to create resources until the applicable contract checklist below is signed off.

## 1. Executive decision

The owner-directed target is a **full-stack Truth-Talk service**: browser application, Truth-Talk-owned API and database, governed media flow, and explicit Rootgate/mesh contracts. A static SPA may be the frontend delivery layer, but a static-only deployment is not completion of this target. Azure remains optional for local execution and Pharo-Lapse peer messaging; offline operation must not depend on Azure. The current `0.4.0` release is still a browser-only React 19/Vite/TypeScript client with no server or database, so the full data plane remains unimplemented.

Use **Azure Front Door Premium** as the public edge, with **Azure Static Web Apps Standard** for the SPA frontend and a separate Truth-Talk-owned API origin. Build the Vite app to `dist`, configure SPA navigation fallback, attach a Front Door Premium WAF policy, and restrict direct frontend-origin access to Azure Front Door using the profile's `X-Azure-FDID` and approved forwarded hostnames. This frontend tier is only one part of the product; the API and private data plane below are required for the requested hosted system. [1][2][3]

The requested data plane is a distinct Truth-Talk-owned backend: **Azure App Service on Linux Premium v3 (P1v3 starting point, minimum three instances across zones where supported)** behind the same Front Door Premium profile using Private Link; **Azure Database for PostgreSQL Flexible Server, General Purpose, D4ds_v5 (4 vCores/16 GiB) with zone-redundant HA where available**, on private VNet access; and a dedicated **StorageV2** account for media. Use **Service Bus Premium (2 messaging units)** only for a separately approved asynchronous application workflow; it does not replace Pharo-Lapse. These are production planning selections, not capacity guarantees. The owner has selected this full-stack direction, but subscription/region/domain decisions and the identity, receipt, data, and recovery contracts still gate actual resource creation and implementation. [4][5][6][7][8]

Use the App Service backend pattern rather than introducing Container Apps or AKS in this first server-backed increment: the supplied research establishes a documented Front Door Premium Private Link path and public-origin isolation pattern for App Service, whereas no current server workload or direct Kubernetes-control requirement exists. Reassess Container Apps for independently scaling queue consumers or event jobs if measured workload justifies that split; use AKS only if validated requirements need Kubernetes API/control-plane access or workload capabilities not met by the managed app services. [9][10][11]

## 2. Non-negotiable trust and operating boundaries

- **Rootgate remains the human identity anchor/front door.** Azure Entra managed identities are workload identities for Truth-Talk-to-Azure access, not human identities and not a substitute for Rootgate. Do not infer Rootgate OIDC support, tokens, claims, scopes, issuer, redirect URI, logout, or API routes; those are blocking unknowns until Rootgate publishes and approves a versioned contract. [12][13]
- **Archangel remains the node-signing/verification authority; Tesseract-A remains Archangel's evidence-verification capability.** Truth-Talk may import and display receipts only according to an agreed, verifiable receipt contract. It must not claim that Truth-Talk independently verified underlying evidence. No Rootgate, Archangel, or Tesseract-A API, key, schema, or trust contract was supplied. These are blockers, not configuration details to guess.
- **Truth-Talk owns its own data boundary.** The requested Truth-Talk API mediates authorization and owns a dedicated Truth-Talk database and media account. Do not share databases, credentials, managed identities, or private signing keys across Truth-Talk, Rootgate, Archangel, or Tesseract-A. The browser must never connect directly to PostgreSQL or contain database credentials or storage account keys.
- **No cloud custody of user signing keys.** Any Nostr/4Reels public broadcast requires explicit user approval and a client-side user-signed event. An Azure worker may relay an approved signed envelope but may not create, receive, or persist the user's private signing key.
- **Local/offline operation is independent.** Local profiles/readiness, local attestations, Nostr/4Reels, evidence workflows, established peers, and Pharo-Lapse's local offline store-and-forward protocol must remain usable with no Azure or Rootgate network connection. Cloud sync/import is optional and may be delayed or unavailable without invalidating local operation.

## 3. Target architecture and provisioning phases

### Phase A — Frontend and edge smoke stage (interim only)

`Browser → Front Door Premium (TLS, WAF, route/cache) → Static Web Apps Standard (Vite SPA)`

This stage tests frontend delivery, TLS, WAF, and routing only. It does not deliver the requested API, database, media flow, identity handoff, or receipt import, and must not be presented as the completed Truth-Talk production system. Use a dedicated Truth-Talk hostname only after the domain owner and DNS authority approve it. Keep Rootgate's hostname and paths untouched; do not take over the apex or another application's route by assumption. [1][2][3]

### Phase B — Owner-directed full-stack backend/data plane (contracts still gate implementation)

`Browser → Front Door Premium → Truth-Talk App Service (Private Link) → private PostgreSQL`  
`                                                    ↘ Truth-Talk media API → private Blob origin`  
`Approved async work, if justified: Truth-Talk API/outbox → Service Bus Premium → idempotent worker`

The API is the only boundary for a future contracted Rootgate authentication/session handoff, Truth-Talk authorization, database operations, receipt intake, media upload authorization, and any queueing. Imported receipts are stored in the Truth-Talk database as the system of record, not solely in a queue. The database is a required Truth-Talk-owned application boundary; do not build a direct Rootgate/Archangel database link. [4][5][6][7][8][12]

### Phase C — Optional scaling split

Only add separately scaled feed, publishing-worker, or WebSocket/relay services after their protocols and load behavior are known and tested. Container Apps can host managed app/job workloads and autoscale from event sources; its ingress supports WebSockets but documents a 240-second request timeout, so persistent relay behavior needs explicit end-to-end testing. Do not promise long-lived relay compatibility on the basis of ingress support alone. If demonstrated requirements need direct Kubernetes control, assess an isolated AKS service rather than moving the whole app by default. [9][10][11]

### Why an Azure Load Balancer alone is insufficient

An Azure Load Balancer is a distinct network load-balancing service; it is not the public HTTP application-delivery layer selected here. This app needs a global Layer 7 entry point that can terminate TLS, route by host/path, cache static assets, health-monitor origins, and attach a web application firewall. Azure Front Door provides those edge delivery/routing capabilities and WAF integration; Microsoft describes Front Door as a global Layer 7 service, distinct from Load Balancer and Application Gateway. A Load Balancer alone does not provide the stated Front Door CDN/WAF/HTTP-routing role. No separate Azure Load Balancer is needed for the static SPA origin. [14][38]

## 5. Preconditions and “do not provision until” contract checklist

### 5.1 Mandatory before any production resource creation

Do not click **Create** for production resources until the owner and Azure administrator have recorded approval for each item:

- [ ] **Subscription and tenant:** Identify the production tenant/subscription, authorized operators, role assignments, policy constraints, quota checks, and whether production use is permitted. Trial eligibility and credits are account-specific; neither is assumed or used as a production dependency. [39][40]
- [ ] **Region and resilience:** Select region(s) based on data residency, user latency, zone support and availability of each selected tier. Confirm Front Door/Private Link, SWA, App Service zone-capable scale unit, PostgreSQL SKU/HA, Service Bus, and Storage replication availability. Approve any paired-region strategy and RPO/RTO. No region or region pair is presumed. [4][5][6][7][8][20][23]
- [ ] **Domain and DNS:** Name the dedicated Truth-Talk host and domain owner; confirm DNS change authority, TXT validation, apex/subdomain decision, certificate process, and Rootgate hostname/path separation. Do not configure a guessed hostname or take over the apex. For a Front Door apex, plan validation/certificate monitoring because the documented managed-certificate autorotation has a validation caveat. [18][19][41]
- [ ] **Security/operations ownership:** Name the service owner, on-call, incident path, access reviewers, log access/retention policy, backup owner, and approval workflow. Define availability, recovery, privacy, legal retention, and data-classification requirements rather than inferring them from Azure service features.
- **Architecture direction:** The owner has selected Phase B, the full-stack backend/data plane, as the target. Phase A alone is not completion. This direction does not substitute for the remaining subscription, region, domain, security/operations, and contract approvals needed before provisioning.

### 5.2 Blocking contracts before Phase B backend/identity/receipt resources

**These are unresolved blockers in the supplied research. Do not implement an identity handoff, API route, receipt importer, verifier, or database schema that assumes them.**

- [ ] **Rootgate API and identity contract:** Rootgate owners publish/version approved issuer and discovery metadata, client registration and stable callback/redirect host, supported flow/scopes, stable subject and claim semantics, audience, session validation/logout/revocation behavior, key rotation, error/retry behavior, and any API endpoints. Confirm Rootgate meets the chosen integration's requirements before configuring it. The supplied sources do not establish Rootgate API/OIDC compatibility or contract. [13]
- [ ] **Archangel/Tesseract-A receipt and key contract:** Owners provide a versioned receipt schema/media type; issuer and verifier identity; receipt/event ID; key ID, trust roots/key publication, rotation/revocation; exact algorithm, digest, serialization/signature encoding; evidence references/hashes; result semantics, scope/limitations, timestamps/freshness/expiry, replay rules, audience/nonce if used; transport authentication, retries, backfill, and availability. The supplied research does not establish Archangel API, Archangel key format, or receipt schema. Do not invent these. [42][43]
- [ ] **Truth-Talk data ownership/schema:** Define what Truth-Talk stores, consent/legal basis, receipt retention/deletion, whether raw evidence may leave the user's device, database roles, account linking, and migration ownership. Store only Truth-Talk-owned records; never share another application's database or private keys.

Default to API-mediated upload for private storage. Direct browser-to-Blob upload needs a separate security decision about endpoint reachability, tightly scoped short-lived user-delegation SAS and exact-origin CORS; CORS is not authorization. [44][45]
- [ ] **Async/Nostr contract, if used:** Define user approval evidence, signed-event envelope, relay selection, acknowledgement and deduplication/retry behavior. Only enqueue already user-signed payloads; Azure never receives a user private key.
- [ ] **Driver and deployment verification:** Validate Node PostgreSQL driver/ORM compatibility, TLS, private DNS/networking, connection pooling, migration runner, and restore/failover behavior against the selected service before production data is written. ORM documentation does not prove deployment connectivity. [46]

## 6. Azure Portal provisioning sequence

Use the Portal to provision only the approved phase. Portal labels may change; resource types and settings below are the requested configuration. Do not substitute a similarly named tier without architecture review.

### 6.1 Phase A: SPA-only production entry

1. **Select subscription and create the production resource group.** In Azure Portal, choose the approved subscription, search **Resource groups** → **Create**, select the approved metadata region, give the group a Truth-Talk production name, apply owner/environment/data-classification tags, and verify policy/role scope. The resource-group location does not select the global Front Door serving region.
2. **Create the Static Web App.** Search **Static Web Apps** → **Create**. Select the approved subscription/resource group, deployment source/repository only after repository authorization, and **Standard** plan. Set the build preset to the actual framework/build command and set the app artifact location to `dist` for Vite. The framework guide identifies `dist` as the Vite output directory; verify the repository build actually produces it before deployment. [1][47]
3. **Prepare routing config before first release.** Include `staticwebapp.config.json` in the deployed artifact. Set `navigationFallback` to rewrite unmatched SPA routes to `/index.html`, with exclusions for real asset paths/extensions. Test direct refresh of client-side routes and ensure a missing JavaScript/image path remains a 404 rather than returning the SPA shell. [2]
4. **Create Front Door Premium.** Search **Front Door and CDN profiles** → **Create** → choose **Azure Front Door**, select **Premium**, and create one profile/endpoint. Add a single origin group and the Static Web App origin. Use the SWA default hostname only as the origin; HTTPS origin communication is required. Create a route for the approved Truth-Talk host and `/*`; configure HTTPS redirect and deliberate caching/compression. Do not register the custom host before the domain owner authorizes DNS changes. [3][14]
5. **Attach WAF.** Create a Front Door WAF policy at Premium tier and associate it to the Truth-Talk domain/security policy. Enable the supplied current managed rule set (DRS 2.2 guidance) and Bot Manager only as appropriate. Start in **Detection**; enable diagnostics, inspect false positives, create reviewed exclusions, then move to **Prevention**. WAF filters web requests; it does not provide app authentication, authorization, receipt verification, or a database. [15][16][17]
6. **Lock down the SWA origin.** In Static Web Apps configuration, use the documented Front Door integration/networking configuration: restrict allowed IP ranges to `AzureFrontDoor.Backend`, require the profile-specific `X-Azure-FDID`, and permit only the Front Door hostname and approved custom forwarded hosts. Confirm direct access to the SWA hostname is rejected while the Front Door route works. Do not copy node IP addresses or credentials into the runbook or configuration notes. [3]
7. **Bind the approved domain and TLS.** In Front Door, add the custom domain and associate it with the route. Publish the required TXT validation record. Use CNAME for a subdomain. For an apex, use an Azure DNS A alias to the Front Door endpoint or an external DNS provider that supports CNAME flattening. Validate domain state/certificate before updating users or clients. Monitor apex validation/certificate state over time. [18][19][41]
8. **Enable diagnostics and alerts.** In Front Door **Diagnostic settings**, send access, WAF and health-probe logs to the approved Log Analytics workspace. Enable SWA/Front Door metrics and configure alerts for origin health, availability, errors and WAF events; diagnostics are not enabled by default. Set workspace region, access and retention per owner policy. [35][36][37]
9. **Validate release.** Confirm HTTPS and redirect, canonical host, expected WAF behavior, cache headers, direct-origin denial, SPA deep-link refresh, missing-asset 404, and a clean browser console. Do not enable sensitive browser telemetry without a privacy review and filtering.

### 6.2 Phase B: API and Truth-Talk-owned data plane (after contract approval)

1. **Approve contracts first.** Complete Phase B checklist in section 5.2, approve threat model/data classification, select database/media/receipt lifecycle, and approve an application/API design. If any Rootgate API or Archangel key/receipt schema remains unknown, stop this phase.
2. **Create VNet and private DNS.** In **Virtual networks**, create the approved region/VNet and dedicated subnets for App Service VNet integration, PostgreSQL delegation, and private endpoints. Configure required private DNS zones and links. Review address capacity, NSGs and routing with the platform/network owner before creating dependent resources. PostgreSQL VNet access requires a delegated subnet and private DNS. [6][22]
3. **Create the Truth-Talk Key Vault and workload identity.** Create a dedicated vault in the approved region/network design, configure RBAC, soft delete/purge protection and diagnostics per policy, and a user-assigned managed identity dedicated to Truth-Talk. Grant minimum secret-read permissions only if a Rootgate confidential-client secret is required by the approved contract. Do not put private signing keys in this vault. ACA/App Service managed identity references to Key Vault avoid application-managed secret credentials; use the documented identity model for the selected host. [12][30][31][32]
4. **Create PostgreSQL Flexible Server.** Search **Azure Database for PostgreSQL flexible servers** → **Create**. Choose the approved resource group/region and **General Purpose**, select **D4ds_v5 (4 vCores, 16 GiB)** as an initial testable size, and provisionally set **256 GiB** storage only if workload sizing still supports it. Select private VNet access/delegated subnet and private DNS; disable public exposure. Enable zone-redundant HA if offered for that region/SKU. Set backup retention per policy (up to the documented 35-day maximum); decide geo-redundant backup before creation because that choice cannot be changed later. Create only a Truth-Talk database and least-privilege role; test managed identity/database authentication, TLS, pooling and failover. [4][5][6][23]
5. **Create media StorageV2 (only after media policy approval).** Create a dedicated general-purpose v2 storage account. Choose ZRS where supported; GZRS only after approving cross-region data recovery/residency. Enable blob and container soft delete. Create separate quarantine and published containers or equivalent isolation. Keep keys out of browser/app configs. For private-network storage, implement a Truth-Talk API-mediated upload. If a separately approved direct upload is chosen, mint only short-lived, single-object, minimum-write user-delegation SAS to quarantine, with exact approved CORS origins/methods/headers; verify uploaded content before promotion. [7][24][25][44][45]
6. **Create Front Door media route (conditional).** Add approved-media Blob origin to Front Door Premium using the supported Private Link storage origin pattern, approve the origin connection, and deny direct public access if that delivery/upload topology supports it. Cache only approved public/immutable content. Use an expiring authorized path for private content; do not expose SAS as the durable media identifier. [26][27]
7. **Create App Service backend.** Create **Linux App Service Premium v3 P1v3** in the approved region, initially minimum three instances across availability zones if the region/scale unit supports zone redundancy. Configure a staging slot, health probes, application settings, managed identity, and outbound VNet integration subnet. Use Front Door Premium Private Link as inbound origin, approve the connection, and disable public network access on the app. Configure API routes only after Rootgate/receipt contracts define their exact semantics. The three-instance selection is an architecture recommendation, not a guaranteed capacity figure. [20][21]
8. **Add database and secret access.** Grant the app identity only the needed Truth-Talk PostgreSQL role and Key Vault secret access, using the selected supported auth configuration. Do not grant the app identity Rootgate administrative access, Archangel key access, or another application's database rights. Keep schema migrations in the Truth-Talk repository and deploy backward-compatible expand/contract migrations.
9. **Add optional Service Bus only if needed.** Create a dedicated **Premium** namespace and queue only for defined asynchronous work; start with **2 messaging units**. Use managed identity and private connectivity where supported. Persist receipt/app state and an outbox in PostgreSQL before sending queue work. Set stable message IDs, but also enforce durable database idempotency: Service Bus duplicate detection is time-windowed and is not a substitute for application deduplication. Define DLQ alert, triage, retention and replay owner before production. This queue is not Pharo-Lapse and must not become a mandatory online broker for local messaging. [8][28][29][48]
10. **Deploy and test.** Deploy API to staging, run contract tests with approved nonproduction Rootgate/Archangel test fixtures, then smoke and security test before production. Test private DB access, secret retrieval, signed receipt validation according to the contract, idempotent retry/DLQ behavior, object quarantine/promotion/delete, Front Door bypass denial, failover, backup restoration, and local behavior when all cloud endpoints are unreachable.

## 7. Application and data behavior

### Truth-Talk-owned database

The database is a future Truth-Talk application boundary, not a shared integration shortcut. Store only product-approved Truth-Talk state: account/profile mapping keyed by Rootgate's agreed stable subject, receipt/import metadata, source-envelope reference or approved proof, verification display state according to the issuer contract, media object metadata, idempotency/inbox records and (if async work exists) transactional outbox. Preserve source receipt bytes/version if the contract and data policy require it. Do not store raw evidence by default; require separate lawful-basis, consent, retention and security approval. [4][5][6]

Receipt intake should validate the agreed envelope and provenance, durably write a Truth-Talk receipt/inbox record and unique idempotency key, and only then acknowledge receipt. If follow-on work is asynchronous, write application state and outbox entry in one database transaction; a relay sends the outbox item to Service Bus, and the consumer is idempotent. Service Bus is delivery/work buffering, not the receipt system of record. Queue delivery may be at least once; design retries and duplicates accordingly. [8][28][29][48]

### Media architecture

Store binary objects in a dedicated Truth-Talk Blob account and keep object keys/metadata—not large media bytes—in PostgreSQL. Uploads enter quarantine; only approved, inspected objects are promoted to public delivery. Public media may use a stable Front Door-hosted URL/object path; private media uses authorized expiring access and appropriate cache controls. Do not store account keys in the client, use long-lived SAS URLs as canonical media IDs, or assume that SAS/CORS performs malware, rights, moderation, or content validation. [7][24][25][26][44][45]

Default to a server-mediated upload while private-network storage is a requirement. A direct browser upload via SAS is a separate design option, not the default; it entails browser access to the Blob endpoint, narrow delegated SAS permissions/expiry, exact-origin CORS, and server-side post-upload validation. CORS is a browser policy and not an authorization control. [44][45]

## 8. Delivery workflow and release controls

For the SPA, build and test the exact commit, upload the Vite output to SWA, verify in a staging environment if used, and promote only an approved artifact. Static Web Apps Standard includes staging environments according to plan documentation. [1]

For a future containerized API, use GitHub Actions OIDC to exchange short-lived tokens rather than saving long-lived Azure credentials. Restrict Entra federated trust to the exact repository, environment and branch/ref; separate nonproduction and production identities and scopes. Use production environment reviewers and protected branch/tag rules. If using ACR, deploy immutable image digests and retain known-good artifacts. Private registry access requires a verified runner and runtime pull path before public access is disabled. [33][34][49][50]

Use a staging slot for API releases, health/smoke-test it, then swap after production approval. Keep DB migrations backward-compatible so old/new app versions can run during promotion; deployment rollback does not undo database changes. Test rollback by swapping back to the known-good build and checking Front Door origin health. [21][51]

Do not assume deployment automation is already configured. Repository ownership, runner access, workload federation, role scope, branch protection and production reviewer rules are explicit prerequisites.

## 9. Security and privacy prerequisites

- TLS from browser to Front Door and HTTPS from Front Door to origin; use custom domains only after ownership/DNS control is established. Restrict origin reachability to Front Door and prevent a publicly reachable alternate path from bypassing WAF. [3][17][20][38]
- WAF Detection-first tuning followed by Prevention; diagnostics and access logs enabled; WAF is not identity/authz/receipt verification. [15][16][17][35]
- Separate Truth-Talk managed identity and data roles; least privilege; no embedded secrets. Managed identity authenticates workloads to Azure services, not end users. [12][30][32]
- Keep PostgreSQL private; use VNet integration, private DNS, TLS, least-privilege database principals, backup/restore testing, and transient-fault retry with bounded backoff/idempotent writes. [4][6][23]
- Keep storage private by default; public delivery is only for explicitly approved published objects. SAS grants scoped permissions for a time window and should be tightly restricted; use user-delegation SAS secured with Entra credentials over account-key SAS where direct upload is approved. [24][26]
- Browser telemetry and application logs must exclude tokens, secrets, user private keys, Nostr content, raw receipts/evidence and sensitive URLs. Set retention/access controls and privacy notice/consent before enabling RUM. [36][37]
- Azure Key Vault's cited algorithm tables do not list EdDSA/Ed25519 or Schnorr; do not infer compatibility from ECDSA support. No Archangel key migration or Azure signing service is in this runbook. Any future key custody decision belongs to Archangel and requires algorithm/wire-format proof and explicit owner approval. [52][53]

## 10. Operational checks and recovery

Before each production release, verify DNS/domain validation and certificate state, Front Door route/origin health, WAF mode and logs, SWA direct-origin restriction, SPA deep links, missing asset behavior, HTTPS redirect, browser error telemetry filtering and deployment artifact version. For backend releases, additionally test API health, Rootgate contract conformance, private database connectivity, authorization boundaries, receipt verification/display according to agreed semantics, idempotency, media quarantine/promotion, and queue DLQ handling if present.

Set Azure Monitor alerts and action groups for Front Door availability/origin health/5xx, synthetic endpoint failures, WAF anomalies, App Service availability/latency/exceptions/resource saturation, PostgreSQL availability/CPU/storage/connections/HA state and backup, Blob errors/availability, Service Bus queue age/depth/DLQ if provisioned, and Azure Service Health. Choose thresholds and notification destinations from SLO/on-call policy; no threshold or retention value is inferred here. Verify alert delivery and retain runbooks. Front Door access, WAF and probe logs must be explicitly enabled. [35][36][37][54]

Recovery is not implied by selecting HA or Front Door. Front Door can route among healthy origins, but does not replicate application state or reverse a bad release. PostgreSQL point-in-time restore creates a new server; geo-redundant backup supports restore to a paired region and is not automatic live failover. Geo-backup is selected at server creation. Conduct restore and connection-cutover drills and record observed RTO/RPO before setting a service commitment. [23][55][56]

Operational runbook:

1. **Edge or origin failure:** Check Front Door health probes/access logs, WAF actions, DNS and origin status. Verify origin restrictions and private origin connection; do not temporarily expose the origin without an approved security exception.
2. **Bad SPA/API release:** Revert to last known-good static artifact or swap the API staging slot back; verify health and user paths. Re-deploy the same digest/artifact in all configured regions. Investigate schema compatibility separately. [21][51]
3. **Receipt processing failure:** Stop acknowledgement until durable receipt/inbox write succeeds. Inspect idempotency key, contract version, issuer/key status, outbox relay and DLQ. Do not mark a receipt verified merely because the message arrived or a signature check passed outside the agreed trust contract.
4. **Database incident:** Check service health, zone failover and connection pool behavior; use the approved restore procedure, restore to a new server when required, verify data and permissions, then explicitly cut over connection configuration. Do not promise a recovery time until tested. [23][55]
5. **Media issue/takedown:** Unpublish or deny the approved object, purge/update edge cache according to the defined process, preserve required audit records, and honor approved deletion/retention policy. Do not treat soft delete as a full backup strategy. [25]
6. **Local/peer independence test:** Periodically run Truth-Talk and Pharo-Lapse with cloud endpoints blocked; verify local attestations, peer workflow, local queueing/store-and-forward and Nostr user-side operations remain available.

## 12. Go/no-go sign-off

A static-only launch can proceed with identity/receipt contracts still unresolved only if it does not contain or imply those integrations and has its own approved domain/security/privacy/release decisions.

Backend/data-plane provisioning is **NO-GO** until every applicable item in section 5.2 is resolved, especially the **Rootgate API/identity contract** and the **Archangel key and Tesseract-A receipt schema/verification contract**. Any unresolved data ownership, region/residency, custom-domain/DNS, RPO/RTO, network-origin, media consent/takedown, or key trust decision blocks the relevant resource or feature.
