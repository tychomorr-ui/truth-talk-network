# Nostr reporting, deletion, and moderation limits

A decentralized Nostr client can verify that an event matches its ID and that its signature is valid for a public key. It cannot, by itself, make a report binding, remove every copy of a post or media file, compel relays to enforce a policy, or prove that a key belongs to the real person depicted or named. NIP-56 reports, NIP-09 deletion requests, and NIP-51 mute lists are protocol signals whose effect depends on the relays and clients that choose to act on them. [1] [2] [3] [5]

## What the protocol does—and does not—do

**Reporting (NIP-56).** A report is an optional kind-1984 event. It identifies the reported account with a `p` tag and, for a note report, includes an `e` tag; the report-type vocabulary includes `nudity`, `malware`, `profanity`, `illegal`, `spam`, `impersonation`, and `other`. For a media blob, the NIP defines an `x` tag for the blob's info hash and requires an `e` tag linking to the event containing that blob reference; a `server` tag may identify a media server. NIP-56 says the concept of objectionable content is subjective and network participants may act as they see fit. Clients may use reports to inform moderation; the NIP specifically discourages relays from automating moderation from reports because reports can be gamed, while noting relay admins could use reports from trusted moderators to take down content prohibited by that relay. A report is therefore not an adjudication, verified allegation, takedown command, or proof that the report is accurate. [1]

**Deletion (NIP-09).** A kind-5 event is a *deletion request*, not a globally enforceable delete operation. It references event IDs with `e` tags or replaceable/addressable event coordinates with `a` tags. The author key must match the referenced event author before a client treats the request as valid. Relays *should* delete or stop publishing matching events, and clients *should* hide them or show a deletion status; the NIP also says clients should broadcast the request to other relays. NIP-09 explicitly says it is impossible to delete events from all relays and clients. It recommends that relays continue publishing deletion-request events indefinitely so clients that already hold the target can learn of the request. A deletion request cannot retract copies already downloaded, screenshots, recordings, exports, caches, or reposts, and deleting the Nostr event does not, by itself, delete a file held at a separate media host. [2]

**Mute and block lists (NIP-51).** The standard kind-10000 mute list represents things a user does not want in their feed, including public keys, hashtags, words, and threads. Lists can include public items in tags or private items encrypted in the event content. It is a user preference clients may use to change that user's browsing experience—not a network-wide block or a requirement for every app to suppress the person. Kind 10006 is specifically a list of relay URLs that clients should never connect to; it is not a user-block mechanism. NIP-51 is marked draft and optional, so compatibility and behavior cannot be assumed across clients. [3]

**Relays and moderation.** NIP-11 relay-information documents are optional. They can disclose supported NIPs, limitations, administrator contact and a terms-of-service link, but the terms link itself is optional; the NIP says a listed administrator has no obligation to respond to messages. NIP-01 describes event acceptance or rejection per relay and explicitly notes that relay implementations may differ. A relay's `OK` acknowledgement is not evidence that other relays received the event or that the event will remain available. NIP-56 leaves report consumption and action to users, apps and relays, and does not prescribe a shared review process, response time, appeal process, or network-wide enforcement mechanism. [1] [4] [5]

**Files and 4Reels.** Nostr events are signed records, while file-sharing conventions point to separately hosted files. NIP-94 describes a file-metadata event with a download `url` and an `x` SHA-256 hash; it also distinguishes `ox`, the hash of the original before upload-server transformations. NIP-B7 describes Blossom as standards for servers storing files by SHA-256 and recommends checking downloaded file bytes against the hash. NIP-51 has a kind-10063 list of a user's Blossom servers. NIP-96, the older HTTP upload/storage integration, is marked `unrecommended` and deprecated in favor of NIP-B7. These sources support a clear boundary: publishing a Nostr event or deletion request is separate from hosting, moderating, and deleting the media object. The 4Reels product label does not add protocol-level moderation or provenance guarantees; short-video content has the same trust and storage limits as other user-generated files. [3] [6] [7] [11]

## What receipts and identity signals prove

**SHA-256 hash.** NIST describes a hash as mapping an arbitrary-length message to a fixed-length digest and characterizes approved hash functions by collision, preimage, and second-preimage resistance. NIP-94 uses SHA-256 for file hashes; NIP-B7 tells clients to verify that downloaded bytes match the 64-character digest. Recomputing a matching hash is useful evidence that the bytes currently checked are the same bytes represented by that digest, subject to the security assumptions of the algorithm and implementation. A hash alone does not identify who created or uploaded a file, establish when it existed, prove that its content or caption is true, show consent or rights, or reveal whether an image/video is a genuine depiction. It is not a timestamp or moderation decision. [6] [7] [8]

**Nostr event signature.** NIP-01 defines the event ID as SHA-256 of the canonical serialized event data and the signature as a Schnorr signature over that ID. If a client correctly verifies both, it can establish that the event data matches the ID and that the corresponding private key signed that event data. This binds the exact signed tags and content—including a media hash, if present—to the public key. It does not establish the key-holder's civil or offline identity, that a human personally authored the event, that the event's claims are true, that the attached media was captured at the event's `created_at` time, or that the media is consensual or authentic. The timestamp is a field in the signed event, not an independent trusted timestamp. [5]

**C2PA Content Credentials.** C2PA manifests bundle provenance assertions and a cryptographically signed claim, with a content binding that can be validated against an asset. A valid credential can support integrity/provenance statements and signer-key/credential identity claims under the validator's configured trust model. The C2PA specification explicitly says it does not assign value judgments about whether assertions are good or bad; the consumer uses signer identity and other signals to decide whether assertions are true. Therefore, a valid C2PA credential is not proof that a scene happened as described, that all edits are disclosed, that the signer is the person shown, or that the signer underwent identity proofing. [9]

**Identity proofing.** NIST's current digital identity guidance describes proofing as establishing that an applicant is who they claim to be to a stated confidence level. It separates identity resolution, evidence validation, and verification that the applicant presenting evidence is the person to whom it was issued; successful proofing establishes a subscriber account in the identity service. A Nostr public key or C2PA signing credential alone does not perform these steps. If Truth-Talk promises stronger anti-catfishing than “this account controls this key,” it needs a separate, clearly described identity-proofing process and a trustworthy binding between its result and the account. Even proofing an account does not prove that every uploaded recording depicts that account holder or is unaltered. [10]

## Implementation constraints for Truth-Talk

- Present NIP-56 as **user-submitted reporting signals**. Do not label a report as verified, imply reports automatically remove content, or promise relay review or a response. Any product-level review or escalation promise needs a separately authorized service and accountable operator.
- Treat NIP-09 as a **best-effort deletion request**. Show request status distinctly from confirmed removal; if checking relay acknowledgements, report only which relays acknowledged or rejected the event. Do not claim “deleted everywhere.” A separate blob-host deletion path and its result are required for the media file, and neither can erase copies already distributed outside those services.
- Treat NIP-51 mute lists as client/account-specific display controls. Distinguish muting an author from blocking a relay (kind 10006). Do not claim that either prevents viewing through other clients or relays.
- A static browser client can verify signatures, hash downloaded files, locally filter a feed, and create a signed deletion/report event only when an authorized signing capability is provided. These client-side controls cannot force an arbitrary relay, blob server, modified client, or cached copy to comply. A signed event is not a moderation queue or database of resolved reports.
- Do not offer direct public uploads of screenshots, screen recordings, documents, videos, or other files as if Nostr relays alone host them. The product needs an expressly selected and approved external media/blob service (or other storage design), with disclosed retention, access, deletion, moderation/reporting and transformation behavior. No server/database approval is present in this scope; absent approval and an identified host, keep uploads disabled or describe the feature as event/link publishing only. If the service transforms media, preserve and clearly label original (`ox`) versus served (`x`) hashes where applicable. [6] [7] [11]
- Describe a hash receipt narrowly: “these exact bytes match this digest,” and, if signed, “this key committed to this digest in this event.” Do not present it as proof of source, uploader identity, upload/capture time, truth, consent, originality, or policy compliance. An independently trusted timestamp or witness/log service would be needed for stronger time-of-existence evidence; that is outside the cited Nostr hash/signature semantics. [5] [6] [8]
- Do not market key verification or C2PA validation as identity proofing or an anti-catfishing guarantee. Any proofing product must state its proofing level and process, what identity attributes are linked to the account, and which content or actions that link does—and does not—cover. [9] [10]
- Build policy controls around what Truth-Talk itself can actually operate: clear reporting affordances, user-facing mute/hide controls, local pre-display safety filters, minimal collection of sensitive report details, and a truthful statement of the external relay/storage dependencies. A browser-only client cannot guarantee end-to-end compliance or prevent a motivated user from bypassing its client-side filters.
