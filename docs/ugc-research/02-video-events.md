# Nostr video and file metadata events

NIP-71 calls kind `22` a regular short-video event and kind `34236` an addressable short-video event. “Short” describes a stylistic feed category for mostly vertical videos; the NIP explicitly says it imposes no actual length or orientation constraint. It defines no mandatory portrait aspect ratio or duration limit. The NIP marks `title` as required. For addressable events, `d` is required and uniquely identifies the video under that author and kind. It does not explicitly mark an `imeta` tag as mandatory, although it says `imeta` is the primary source of video information. NIP-71 is currently marked draft/optional. [1]

For a Reel-style short, use kind `22` for a regular event or `34236` if the product needs an addressable/updateable event; both express the “short” convention, not validated verticality. Include `title`. For `34236`, include `d`. Where `imeta` is used, NIP-92 requires its variadic fields to include `url` and at least one other field; each item is a space-delimited key/value string, and there should be only one `imeta` tag per URL. NIP-71 recommends `duration` in seconds and `bitrate`; `dim` can describe the actual pixel dimensions, but neither turns kind `22`/`34236` into a verified portrait-only type. NIP-71 supports multiple `imeta` variants, each with its own URL, MIME type, and hash. Its `fallback` URLs are alternative locations for the same file and are to be treated on par with the primary URL. [1] [2]

NIP-94 defines kind `1063` as a file-metadata event. Its field meanings are: `url` is the URL to download the file; `m` is the MIME type string, using MIME syntax and lowercase as the NIP’s stated convention; `x` is the hex-encoded SHA-256 of the file; and `ox` is the hex-encoded SHA-256 of the original file before upload-server transformations. Optional metadata include size, dimensions, preview/thumbnail, alternative sources (`fallback`), accessibility text, and service. The NIP’s bullet definitions do not explicitly state a `MUST` requirement for `url`, `m`, or `x`; do not invent one from the example. NIP-92, by contrast, explicitly requires `url` plus at least one other field when an `imeta` tag is present. [2] [3]

**Hash and signature are different receipts.** A SHA-256 `x` value can be used to check whether downloaded bytes match the event’s declared digest: recompute SHA-256 over the exact bytes and compare. NIST describes digests as a means to detect changes since digest generation. The hash alone does not identify who created, captured, or uploaded those bytes; prove they depict a real event/person; establish when they existed; or keep the file available. `ox` is a separate digest for the pre-transformation original, not a guarantee that the client possesses or can retrieve it. If a host transforms a file, the digest of the transformed served bytes and the original digest can differ. [3] [4]

NIP-01 defines an event ID as SHA-256 of the canonical serialized event data and `sig` as a Schnorr signature over that ID, with the event’s `pubkey` identifying the public key to verify against. A valid signature therefore authenticates the event’s contents—including its URL/hash claims—as signed by the corresponding key; it does not authenticate the media bytes unless the client separately downloads and verifies the declared hash. Nor does possession/control of a Nostr key prove the controller’s legal name, age, uniqueness, humanity, or real-world identity. NIP-71’s optional participant `p` tags are likewise references to public keys, not identity checks. [5] [1]

C2PA Content Credentials, if included in a media file and independently validated, can bind a manifest to covered asset bytes and verify that signed provenance assertions are correctly associated and untampered under the standard’s validation model. C2PA’s own principles say its specifications do not judge whether provenance assertions are good or bad, and do not require the identity of the asserting person or organization to be documented. A valid credential is therefore not, by itself, proof that the depicted scene or assertion is truthful, that a person shown is who they claim to be, or that identity proofing/liveness occurred. Treat C2PA as an additional provenance signal, not an anti-catfishing or truth guarantee; the spec’s trust model depends on signer credential identity, whose meaning depends on the credential and trust configuration. [6] [7]

NIP-09 defines kind `5` deletion requests. Relays *should* delete or stop publishing matching events from the same author, and clients *should* hide or mark them, but the NIP explicitly says deletion cannot be guaranteed across all relays and clients. A deletion request is not a global erasure mechanism; copies, caches, screenshots, and downloaded media may persist. NIP-56 kind `1984` reports are optional signals about objectionable content; agents may decide how to act, and the NIP warns that automatic relay moderation based on reports is gameable. These mechanisms do not supply a universal moderation or policy-compliance guarantee. [8] [9]

## Implementation constraints for Truth-Talk / 4Reels

- Treat “short/vertical” as a product filter and inspect actual media dimensions if portrait presentation is required. Do not claim NIP kind selection proves video orientation, duration compliance, original capture, or identity.
- For each media rendition, bind its own `url`, lowercase MIME `m`, SHA-256 `x`, and actual dimensions through `imeta`; validate hashes against fetched bytes before showing a “hash verified” receipt. Label `ox` separately as the original-byte digest where server-side transformation occurred. Metadata tags are publisher-supplied claims until independently checked.
- Keep the signed-event receipt separate from the file-integrity result: show which public key signed the URL/hash metadata, whether the event signature verifies, and whether retrieved bytes match `x`. Do not label either as “identity verified,” “authentic footage,” or “truth verified.”
- A static Nostr client can reference externally hosted media in signed events, but the video/file event specifications do not provide the hosting itself. Publishing still depends on Nostr relays, and resolving media depends on external URLs or mirrors. No upload server/database is implied or authorized by these specifications; keep upload/hosting out of scope until explicitly approved. Also, the current NIP-96 source is marked `unrecommended` and deprecated in favor of NIP-B7, so do not assume a NIP-96 service is the approved upload path. [1] [3] [5] [10]
- Implement moderation as a clearly scoped client/relay policy layer, not as an inherent property of Nostr. Reporting, local hiding, warnings, relay filtering, and file-host takedown are distinct mechanisms; communicate that removing an event does not necessarily remove its media or copies.
- Anti-catfishing needs a separately specified identity-proofing and impersonation response policy. Neither signed posts, matching file hashes, C2PA credentials in general, nor `p` participant tags provide that capability by themselves. NIP-56 offers an impersonation report category, not a verified identity or adjudication system. [1] [5] [6] [7] [9]
