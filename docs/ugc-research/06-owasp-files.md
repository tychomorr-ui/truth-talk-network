# Secure handling of user-uploaded media and documents

## Findings

OWASP treats upload security as defense in depth: no single file check makes user content safe. It recommends a narrowly scoped allowlist of extensions needed for the product, input validation before extension checks, and rejecting rather than relying on a denylist. Decode and normalize filenames before evaluating them; account for double extensions, case changes, null-byte and path tricks. The filename, declared MIME type, and extension are untrusted metadata. MIME is useful only as a quick check, and a file signature is an additional check—not a sufficient one by itself. Browser-only checks are bypassable; OWASP says to validate on the server even when the browser repeats the checks. [1] [2]

For any accepted type, validate the actual structure with an appropriate parser/decoder rather than inferring safety from its label. OWASP recommends decoding and re-encoding images to an allowed format and removing unnecessary metadata, while warning that rewriting does not guarantee removal of all malicious content and that the image processor itself is exposed to hostile input. Use current libraries with restricted formats, resource limits, and sandboxing. OWASP says to consider Content Disarm and Reconstruction (CDR) for applicable documents such as PDF and DOCX, does not recommend ZIP uploads, and says malware scanning or sandboxing should be used when available. A public malware-scanning service can itself leak data; OWASP explicitly cautions about leakage and information gathering when using such services. [1]

Bound the whole resource-consumption path, not just the browser-selected file: cap file size and request size; account for decompressed size and safe archive processing if archives are ever supported; and limit downloads to reduce denial-of-service exposure. The cheat sheet identifies parser exploits, phishing files, ZIP/XML bombs, storage exhaustion, overwrite attacks, and public client-side active content (including XSS/CSRF) among the risks. It also notes that publicly retrievable files may expose personal or illegal/offensive content and can make the host responsible for handling abuse. OWASP recommends user reporting and copyright-abuse reporting, and—where resources permit—manual review in a sandbox before public release. [1]

For storage, OWASP's preferred arrangement is a different host for uploaded files; next best is outside the application webroot. If a product serves public files, it recommends a handler rather than exposing storage paths. Its HTTP-header guidance says user-provided files should be downloaded with `Content-Disposition: attachment`, unknown/binary types should use `application/octet-stream`, and responses should set `X-Content-Type-Options: nosniff`; use an accurate `Content-Type` for any deliberately rendered safe media. These controls reduce unintended browser execution, but they do not substitute for validation or sanitization. [1] [3]

A static browser client cannot itself provide the server-side boundary OWASP describes. Client-side checks may improve usability and stop accidental mistakes, but a user can bypass the client and submit directly to a storage endpoint. If the product does not approve a separately operated storage/processing service, it has no approved place to enforce upload limits, decode and inspect content, scan or disarm documents, control response headers, quarantine pending review, or administer removal. Nostr is not the binary-upload store: current NIP-B7 describes Blossom servers for files addressed by SHA-256, and NIP-96 (the former HTTP file-storage API) is marked deprecated in favor of NIP-B7. Thus decentralized signed posts do not remove the external media-host dependency for public uploads. [2] [6] [7]

## Hashes, signatures, provenance, identity and deletion

A SHA-256 digest is a fingerprint of particular bytes. NIST describes message digests as a way to detect whether a message changed after the digest was generated. If the client hashes a selected file and a downloader independently hashes the received bytes, a match supports byte-for-byte consistency with that reference digest. It does not establish who created or uploaded the file, when it was created, whether it depicts a real event, whether it is benign, or whether the digest was honestly associated with the file in the first place. A hash is not encryption, malware scanning, identity proofing, or a guarantee that a URL will remain available. NIP-94 distinguishes `ox` (the original-file SHA-256 before transformations) from `x` (the saved/transformed-file SHA-256); a product should name which exact byte version each receipt covers. [4] [5] [12]

NIP-01 defines an event ID as SHA-256 of canonical serialized event data and the Schnorr signature as a signature over that ID, using the event author's public key. Verifying the event establishes that the event data (including a hash or URL in it) was signed by the corresponding private key and has not changed without invalidating the signature. It does not establish a real-world person's identity, honest capture, truthful claims, safe bytes, or an independently trusted publication time; `created_at` is an event field supplied by the signer. NIP-98 similarly defines signed HTTP authorization bound to a URL and method, with an optional request-body hash; that authorizes a request in a server's protocol, not the safety or truth of its file. [4] [8]

C2PA Content Credentials can cryptographically bind provenance assertions to an asset and make the credential/asset tampering-evident. C2PA expressly does not judge whether the assertions are true or whether the depicted content is accurate or factual. Credentials may be absent, removed, or incomplete; the core specification does not itself establish the human identity of the creator. C2PA can contribute provenance signals, but it is not an anti-catfishing or content-truth guarantee. NIST identity proofing is a separate process for associating an applicant with a real-life identity at a stated assurance level; a Nostr key, file hash, or C2PA signature is not a substitute for that process. [9] [10]

Deletion must be described as a request or a service-specific action, not guaranteed erasure. NIP-09 says relays should delete or stop publishing referenced events and clients should hide or indicate them, but explicitly notes that it is impossible to delete events from all relays and clients. NIP-96 describes an authenticated delete request to the file server; with deduplicated files, deletion can remove one user's ownership association while preserving the shared bytes for other owners. Neither mechanism erases downloads, caches, backups, reposts, or copies held by other services. NIP-96 also says a requested expiration need not be honored by the storage service. A durable moderation/takedown policy therefore requires an accountable storage and operations layer and must make residual copies clear. [6] [11]

## Product constraints for Truth-Talk / 4Reels

- **Do not enable public file upload on a static-client-only basis.** Keep uploads disabled until an approved media-storage service (whether operated by the product or a consciously selected third party) contractually and technically provides server-side allowlist enforcement, content inspection, hard byte/request limits, safe storage and serving, abuse intake, and an operational takedown route. A client-side preflight cannot satisfy those controls. This is an implementation constraint derived from OWASP's server-side validation and storage controls, not a claim that OWASP approves a particular vendor or architecture. [1] [2]
- **Use a minimal allowlist per feature.** Define exact file extensions, MIME types, and parsers that the service supports. Reject mismatches and validate signatures/structure together; never accept based on extension or `Content-Type` alone. Do not accept archives, executables, HTML/SVG/XML, macro-enabled documents, or other active/compound formats by default. Treat any format that needs active rendering or complex parsing as download-only or disallowed until the service can isolate, inspect, sanitize/re-encode, and safely serve it. The exclusions are a conservative product policy based on OWASP's active-content and parser risk guidance, not an exhaustive OWASP list. [1] [2] [3]
- **Set explicit bounds before launch.** Define per-file and per-request byte ceilings; for 4Reels, also impose service-side duration, resolution, frame-rate and processing-time ceilings. Bound the maximum decoded image dimensions and any decompressed/expanded content. Enforce quotas and rate limits at storage/relay infrastructure, not only in JavaScript. OWASP specifically calls for size and request limits and consideration of decompressed size; media-specific numeric thresholds remain a product decision and must be tested against cost and abuse requirements. [1]
- **Serve conservatively.** Use a distinct media origin/host separated from the client application. Serve non-previewable and unknown formats as attachments with `application/octet-stream` and `nosniff`. Render only explicitly supported, validated outputs; prefer generated thumbnails and re-encoded still images. Do not inline arbitrary PDFs, office documents, SVG, HTML, or raw user-provided embeds in the app. For video, use only server-validated/transcoded outputs and avoid arbitrary remote embeds. A static client cannot set or verify response headers on a third-party media origin. [1] [3]
- **Make receipts precise and verifiable.** Hash the exact original bytes at selection and verify downloaded media against an advertised SHA-256 before presenting a “hash verified” state. If processing changes the media, record separate original (`ox`) and served/transformed (`x`) digests, with clear labels and a signed Nostr event containing the relevant digest and media URL. Do not call the hash or event signature proof of truth, human identity, capture, malware-free status, publication time, or permanent availability. [4] [5] [6] [7]
- **Separate identity claims from key ownership.** Label a verified Nostr signature as “signed by this key,” not “verified person.” If “anti-catfishing” means confirming a natural person's real-world identity, specify and independently operate identity proofing with its own assurance, privacy, appeals, recovery, and abuse model; do not infer this from a face in an uploaded video, a file hash, or C2PA. Avoid requiring sensitive documents unless the product has a separately reviewed, privacy-preserving process for handling them. [4] [9] [10]
- **Build for public persistence and privacy loss.** Before upload/signing, warn that the public post and media URL may be copied, cached, mirrored, or indexed; ask for deliberate confirmation. Strip unnecessary image metadata during trusted server-side re-encoding and give a pre-publication warning/preview for sensitive screenshots, screen recordings, documents, filenames, location clues, or visible personal data. Never send private uploads to a public scanning service without an explicit privacy review and disclosure. OWASP specifically supports image metadata removal and cautions about public scanning data leakage; the broader user-warning and screenshot/document review controls are prudent product requirements. [1]
- **Do not promise global deletion or complete policy compliance.** Provide report flows, trained review/escalation, copyright/illegal-content response, storage-provider contacts, and transparent status for moderation/takedown. Explain separately what removal from the product's client, a Nostr relay deletion request, and media-server deletion actually do. Without control of third-party relays, media servers, caches and copies, the product cannot guarantee universal removal. [1] [6] [11]

## Uncertainty and scope notes

OWASP's File Upload Cheat Sheet is general web-application guidance, not a validation matrix for every image, video, PDF, or office-file codec. It gives no product-specific size or video-duration thresholds and does not certify that a given sanitizer, scanner, or third-party host is adequate. Those choices require implementation-specific threat modeling and testing. [1]

NIP-96 is explicitly deprecated in favor of NIP-B7 in the current NIPs text reviewed here. NIP-B7 points clients to the Blossom BUDs for upload and file management but does not itself specify a universal moderation, malware-scanning, retention, or takedown guarantee. A particular provider's behavior and terms must be evaluated separately. [6] [7]

The reviewed OWASP and protocol sources do not define a complete social-network policy/compliance program, nor a global enforcement mechanism for Nostr. No legal conclusion is made here. Any regulatory duties, retention rules, illegal-content escalation requirements, and provider-specific obligations need qualified review for the actual jurisdictions and service design.
